# Джерело та межі моделі

## Перевірка реального джерела 21.10.2026

URL: https://kyiv.digital/storage/air-alert/stats.html — єдине джерело автоматичної історії.

- Отримано HTTP 200, `Content-Type: text/html; charset=utf-8`.
- Повна таблиця `<table><tr><td>`: `HH:MM DD.MM.YY`, тип події, текстова тривалість для відбою. Порядок — від нових до старих.
- На момент перевірки HTML мав 5455 рядків подій до фільтрації неоднозначних міток. Після застосування періоду від 01.09.2026 та граничного попередника збережено 680 подій / 340 інтервалів.
- Відповідь містила `Last-Modified: Wed, 21 Oct 2026 05:55:38 GMT`; `ETag` відсутній. Перевірений `If-Modified-Since` повернув **HTTP 304**.
- У HTML не знайдено API-запитів чи пагінації. Доступність окремого недокументованого API не доведена; застосунок його не використовує.
- Джерело захищає Cloudflare. Успішний локальний запит не гарантує успішний доступ з усіх адрес хостингу.

Одна перевірка — один умовний GET. При 200 отримується повна сторінка; це не інкрементальне завантаження історії по API. У SQLite змінюються лише додані, виправлені чи вилучені події. Записи не видаляються фізично: зміни журналюються, старі записи вимикаються. При 304 немає повторного парсингу подій. Повторні спроби при транспортному збої/429/5xx можуть спричинити додаткові запити. Різке скорочення історії понад 20% вимагає перевірки, попередня історія зберігається.

Мітки до хвилини не містять UTC-зміщення. Звичайні локальні години переводяться через IANA Europe/Kyiv. Неоднозначні/неіснуючі години переходу часу в межах періоду **не перетворюються на вигадані UTC-події**: зберігається сирий рядок у `source_issues`, відповідні дні та інтервали позначаються неповними. Час проблеми є верхньою межею невизначеності, а не міткою події. Неоднозначні старі рядки до налаштованої початкової дати пропускаються. При потребі адміністратор додає відому подію з явним UTC-зміщенням; попередження джерела зберігається до виправлення джерела.

Неможливо автоматично довести відсутність тихих пропусків, коли джерело пропустило і початок, і відбій. «Повна доба» тут означає, що вона покрита отриманою історією й немає виявлених суперечностей; це не незалежна сертифікація джерела.

## Спарювання й ручні події

Події сортуються в UTC. Початок без відбою залишається відкритим. Два послідовні початки створюють невизначений проміжок; відбій без початку — зауваження. Від’ємна/нульова тривалість не зараховується. Джерело має хвилинну точність; текст тривалості порівнюється з різницею міток із допуском 1 хвилина. На перевіреній історії є дві більші розбіжності.

Ручні події мають окреме походження, захищений паролем доступ, CSRF і журнал виправлень. Якщо існує рівно один відповідний запис джерела тієї самої події в межах менш ніж 60 секунд та немає конкурента, ручний запис посилається на нього й не дублює інтервал. Неоднозначний збіг позначається конфліктом. Віддалені події не зливаються лише через схожість. Скасування ручного запису зберігається в аудиті.

## Прогнози

- Історичні аналоги — той самий локальний час попередніх повних днів. Для початку потрібні неактивні аналоги з повністю відомим горизонтом; використано спільну поправку Джеффріса `(k+0.5)/(n+1)`. Потрібно 14 аналогів. Монотонність 15/30/60 хв виконується за побудовою.
- Тривалість нової тривоги — медіана й 25–75-й перцентилі завершених інтервалів. Для активної беруться лише історичні тривалості, довші за вже минулий час, та рахуються їх залишки. Мінімум — 10 аналогів. Це проста умовна емпірична модель, не повна survival-модель з цензуруванням; виключення незавершених інтервалів може давати зміщення, особливо після довгих тривог.
- Кількість до опівночі — середнє початків **після** відповідного часу на попередніх повних днях, округлене до цілого; інтервал 10–90-й перцентилі, включно з нулем. Поточна тривога не стає майбутнім початком.
- Початковий день та неповні/суперечливі дні виключаються з аналогів. Для тривалості використовуються однозначні закриті інтервали. Навчання використовує лише попередні доби; поточний статус може враховувати вже відомі події поточної доби.
- Регуляризований логістичний кандидат має L2-регуляризацію та ознаки синус/косинус часу доби й вихідного дня. Він оцінюється лише командою `evaluate`. Обчислення детерміновані, без зовнішніх AI API, sklearn чи важких системних залежностей.

`evaluate` послідовно розширює навчальне вікно, перевіряє 00/06/12/18 за Києвом, не перемішує записи. Порівнює Brier score історичної моделі, постійної згладженої бази й логістичного кандидата; зберігає калібрування 60-хвилинного горизонту, MAE кількості та фактичне покриття її інтервалу. Результат зберігається у `meta.evaluation` та виводиться командою `evaluate`. Невеликий тест із залежними спостереженнями не доводить стійкості в майбутньому. Немає автоматичного перемикання на складнішу модель.

Поточна модель не передбачає військових рішень чи змін тактики. Відсотки не є сигналом безпеки. Панель завжди містить: «Статистична оцінка. Орієнтуйтеся на офіційні оповіщення».
